# PostgreSQL through Drizzle, with checked-in forward-only migrations

The app's data lives in PostgreSQL 18, reached with the standard `pg` driver over one `DATABASE_URL`. The tables are declared once, in TypeScript, as a Drizzle schema in `libs/persistence`, and query types follow from it. Every schema change is a SQL file generated by `drizzle-kit generate`, reviewed and checked in next to the schema. A standalone migrate script applies the files, and the production start command runs it before the server starts. Migrations only go forward: a bad one is fixed by a new one.

PostgreSQL keeps the host choice open, because every host that runs a long-lived Node process pairs with a free managed PostgreSQL, and it has the 64-bit integer that amounts need. Drizzle was chosen because Better Auth's CLI emits its tables as Drizzle schema, so our tables and its tables share one schema and one migration path.

## Considered Options

- **SQLite as a file on the host.** Rejected: it needs a persistent disk, which would decide the host from here and rules out the free tier that has none.
- **Hosted SQLite (Turso, Cloudflare D1).** Rejected: a less common driver and a second dialect for Better Auth's tables, for nothing PostgreSQL lacks.
- **Kysely.** Rejected: table types are written by hand or generated from a live database, and Better Auth's tables arrive as a separate SQL file to fold into our migrations.
- **Prisma.** Rejected: its own schema language and a generated client, the furthest of the three from SQL.
- **`drizzle-kit push`.** Barred everywhere, including locally: it leaves no record of what ran and can drop a column in a statement nobody read.
- **Migrating from a host release hook or a CI step.** Rejected for now: a hook ties the decision to one host, and a CI step puts the production connection string in GitHub. The script can move into a hook if the chosen host has one.
- **PGlite or Testcontainers for tests.** Rejected: PGlite is a different build of the engine behind a different driver, and Testcontainers adds container networking the dev container's own database service already solves.
- **A trigger or a restricted role to enforce the append-only ledger.** Rejected: the persistence library exposes only insert and read for ledger tables, and the test setup must be able to empty them. A trigger can be added later without touching data.
- **Serializable isolation with retries.** Rejected in favour of the group row lock below, which needs no retry code.

## Consequences

- **Every write to a group locks that group's row first.** Each operation is one transaction, and joining or adding an expense takes the lock, so writes to one group happen one at a time. Without it, an expense recorded while someone joins could store shares that do not cover the members at recording.
- **Join order is a stored position per member** (creator 1, then 2, 3 and so on), assigned under that lock. A joined-at time alone can tie.
- Local development and tests use a real PostgreSQL 18 service in the dev container. Each test worker has its own database, built from the checked-in migration files and emptied between tests, so the migrations are exercised on every run.
- Our tables use version 7 UUIDs generated by the database, which is why the version is 18 or later. Better Auth's tables keep the string ids it generates.
- Amounts and shares are `bigint` columns read as JavaScript numbers, safe under the cap in ADR 0003, with a check constraint for the allowed range.
- The managed provider may suspend an idle database, so the connection pool must tolerate dropped idle connections.
- There are no down migrations to fall back on; a production schema change is reviewed as a SQL file before it merges.
